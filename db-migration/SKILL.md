# Database Migration

Do not assume a framework, language, database, migration path, filename shape, or version scheme. Discover them from the current project before making changes.

## Discover the migration mechanism

Read repository instructions first. Then search the checked-out project for migration configuration, framework dependencies, migration runners/loaders, schema history tables, existing migration files, and documented commands. Useful search concepts include `migration`, `migrate`, `schema`, `flyway`, `liquibase`, `alembic`, `prisma`, `typeorm`, `knex`, `goose`, and `dbmate`, but follow evidence rather than requiring these names.

Identify all of the following before creating a migration:

- the database or datastore being changed;
- the authoritative migration directory or schema source;
- whether migrations are generated by a project command or created manually;
- filename and version format, including padding, timestamps, separators, suffixes, and up/down pairing;
- ordering and uniqueness rules enforced by the migration tool or loader;
- whether migrations are forward-only, reversible, transactional, immutable after release, or split by module/database;
- the project's required validation and test commands.

Prefer the project's migration generator when one exists. Do not invent a parallel convention. If evidence conflicts or there are multiple candidate stores, resolve the target from the requested feature and its persistence code; ask the user only when that choice remains materially ambiguous.

For a complete discovery-to-verification example, read [references/tavern-one-shot.md](references/tavern-one-shot.md). It is a worked example, not a source of defaults: re-discover every path, rule, version, and command in the project currently being edited.

## Decide whether a migration is required

Create a migration when the change affects persisted database structure, including:

- creating, renaming, altering, or dropping a table or column;
- adding, changing, or removing an index, primary key, foreign key, unique constraint, default, nullability, or column type;
- adding database objects or schema-level compatibility required by application code.

Do not create one for application logic that works with the existing schema, validation or API-only behavior, configuration, frontend-only changes, or isolated test fixtures. Whether a data backfill belongs in a migration, application/store code, or a separate job is project-specific; inspect existing policy and precedent instead of assuming.

If application code starts reading or writing a new field, verify whether its column already exists before deciding. When uncertain, inspect the model, SQL statements, and all existing migrations.

## Allocate and control the version

Treat the current checkout plus the project's authoritative migration metadata as the source of truth. Never guess a version from memory, an issue, or a stale listing.

Immediately before creation:

1. Enumerate the complete migration set in the target scope, including untracked working-tree files.
2. Derive the version parser and ordering rule from the actual tool/configuration/loader, then confirm it against existing filenames. Do not assume lexical ordering equals migration ordering.
3. Check duplicates, malformed identifiers, forbidden gaps, paired-file requirements, and dependency ordering according to that mechanism.
4. If the framework provides a generator, invoke it and verify its output. Otherwise allocate the next identifier using the observed rule: for example numeric `max + 1`, a framework timestamp generator, or the project's documented semantic sequence.
5. Re-enumerate after creation and verify that the new identifier is unique and ordered where intended.

Do not force every project into three-digit contiguous numbering. A sequence may intentionally allow gaps, use timestamps, contain branches, or be tracked in manifests. Likewise, do not create `.up.sql`, down files, or SQL at all unless the discovered mechanism requires them.

Assume applied or shared migrations are immutable unless project evidence explicitly says otherwise. Never modify, delete, or renumber an existing migration merely to fit a new change.

Concurrent branches can allocate colliding or incorrectly ordered identifiers. After merging or rebasing, repeat discovery and validation. Preserve already-applied/shared migrations. Regenerate or rename only a migration proven to be local and unapplied, using the framework's supported workflow, then update explicit dependencies, checksums, manifests, tests, and code references as required.

## Ensure repeatable validation

Determine whether the project already has a reliable, local validation path. It is sufficient only if it checks the migration invariants actually enforced by the discovered mechanism, covers the complete target migration set, returns a failing exit status for violations, and can run without mutating or connecting to a real/shared database. A framework command, repository test, build task, or existing script may satisfy this; verify its behavior instead of inferring reliability from its name.

When no reliable validation exists and the current task authorizes repository changes, create a project-specific, read-only validation script. Derive its behavior from the evidence gathered above; do not copy assumptions from this skill or another project. The script should:

- live in the repository's conventional tooling location and use its established language/runtime when practical;
- encode the discovered migration roots, scope boundaries, filename/version parser, ordering rule, uniqueness policy, gap policy, paired-file or manifest requirements, and any explicit dependency rules;
- include untracked migration files when validating the working tree;
- print actionable diagnostics that identify the conflicting or malformed files and exit nonzero on failure;
- avoid network access, database writes, and dependence on a live database for structural checks;
- expose one documented, non-interactive command suitable for local use and CI, without changing CI configuration unless requested or already required by repository policy.

Prefer a layered validator when the project structure supports it:

1. Put a thin executable entry point in the project's conventional tooling location and expose it through the existing task runner.
2. Perform fast, database-free manifest checks there: enumerate the authoritative directories, parse identifiers exactly as discovered, and enforce naming, uniqueness, ordering, gap, pair, and dependency rules.
3. Add a narrowly targeted test in the project's implementation language that calls the real production migration loader or parser. Have the entry point run only that safe test, so validation detects drift from runtime behavior without invoking unrelated or destructive integration tests.
4. Keep migration-specific semantic compatibility assertions in focused tests when a change has invariants that filename validation cannot prove.

Use only the layers that add coverage in the current project. If the production migration API cannot be called safely without a database, test its pure parser/manifest component or keep the validator structural; never connect to a real/shared database just to mirror runtime validation.

Test a generated validator against the valid current migration set and in an isolated temporary fixture containing representative invalid cases for the discovered rules, such as a duplicate identifier, malformed filename, forbidden gap, missing pair, or broken dependency. Test only applicable cases; do not invent constraints the migration mechanism does not have.

If the task is explicitly read-only, do not add the script. Report that reliable validation is missing and describe the project-specific validator that should be added.

## Write the migration

- Follow the discovered format and project conventions; migrations may be SQL, source code, XML/YAML, declarative schema changes, or generated artifacts.
- Design for the actual database/version and existing data. Account for nullability, defaults, locking, transaction boundaries, constraint validation, index-name uniqueness, and rollout compatibility where relevant.
- Keep schema and data operations in the locations required by project policy. Make destructive or irreversible operations explicit and do not expand their scope without authorization.

## Verify

Run the project's own validation or the project-specific validator created above, plus formatting and relevant tests. Inspect the diff for unintended generated changes and confirm the final identifier against the complete migration set. Do not run integration or migration commands against a real/shared database, or tests documented as destructive, without explicit permission.
